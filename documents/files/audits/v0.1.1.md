# Application Audit Report
## 1. Critical Bugs & Bottlenecks
### ⚠️ Memory Leak: No Session Cleanup
The GameServer.sessions map is never cleaned up. When a game is created via POST /games, it is added to the map and stays there forever.

Location: code/backend/api/server.go
Impact: Memory usage will grow linearly with the number of games played until the server runs out of RAM.
Fix: Implement a cleanup mechanism in handleGameOver or a background task that removes finished or inactive sessions from the map.
### 🐛 Frontend-Backend Communication Mismatch
The board setup management will fail because the frontend and backend disagree on how IDs are passed.

Location: code/frontend/src/lib/api/client.ts vs code/backend/api/server.go
Issue: Frontend sends PUT /board-setups?id=123, but Backend expects PUT /board-setups/:id.
Impact: Users cannot update or delete their board setups.
### 🐢 Inefficient Game Listing
The HandleListGames endpoint iterates over every active session and calls GetGameState() which performs multiple calculations.

Location: code/backend/api/serverHandlers.go
Impact: If thousands of games are active, this endpoint will become extremely slow and hold a read-lock on the server's session map for too long.
Fix: Cache a summary of active games or use a more efficient data structure for listing.
## 2. Security Vulnerabilities
### 🔓 CSRF Protection Bypass
The CSRF protection is currently "Security Theater."

Issue: The frontend hardcodes X-XSRF-TOKEN: '1'. The backend middleware only checks if the header is non-empty.
Impact: An attacker can easily include this header in a cross-site request (if they can bypass CORS, which is also currently quite open).
Fix: Implement a proper Double Submit Cookie pattern or synchronized token.
### 🔐 Custom JWT Implementation
You have implemented your own JWT signing and verification logic.

Location: code/backend/auth/jwt.go
Risk: While your implementation uses HMAC-SHA256 and constant-time comparison (good!), custom crypto/auth logic is prone to subtle bugs.
Recommendation: Use a battle-tested library like github.com/golang-jwt/jwt/v5.
### 🍪 Cookie Security
Issue: The session cookie does not set the SameSite attribute.
Impact: Increased vulnerability to CSRF in older browsers.
Fix: Set SameSite to Lax or Strict in auth/middleware.go.
## 3. Code Quality & Architecture
### ⚡ Race Conditions
There is a potential race condition between the Game Monitoring Loop and the Game Runner.

Issue: The Game engine (code/backend/game/game.go) is not thread-safe, but it is accessed by both the runner goroutine (to make moves) and the monitoring loop (to broadcast state).
Impact: Rare, hard-to-debug crashes or inconsistent game states sent to clients.
Fix: Ensure all access to the engine.Board and game.Game objects is protected by the GameSession mutex.
### 🚦 Database Context Usage
Issue: Database queries in code/backend/db/queries.go do not accept or use context.Context.
Impact: Requests cannot be cancelled if a user disconnects or a timeout occurs, potentially leading to resource exhaustion under high load.
### 🧹 Inconsistent Package Managers
Issue: The frontend contains both bun.lock and pnpm-lock.yaml.
Impact: Confusion for contributors and potential version mismatches if different developers use different tools.
Fix: Stick to one (preferably Bun based on your rules) and delete the other.


## 🛡️ Security Audit
### 1. CSRF "Cold Start" Vulnerability
Finding: The CSRFMiddleware is applied globally and blocks all non-GET requests missing the X-XSRF-TOKEN header/cookie.
Risk: A guest user who hasn't received a cookie yet (from a GET request) will be unable to log in or register (POST requests). They will receive a 403 Forbidden error.
Location: api/server.go:176, api/middleware.go:16
Recommendation:
Exempt /users/login and /users/register from CSRF validation.
Alternatively, provide a /csrf-token GET endpoint for the frontend to initialize.
### 2. Long-Lived JWTs & No Revocation
Finding: JWTs are signed with HS256 and have a 30-day expiration (maxCookieAge). There is no mechanism to invalidate a token (e.g., if a user logs out on one device but the token is stolen).
Risk: High window of opportunity for attackers if a token is compromised.
Location: auth/jwt.go:34, auth/const.go:3
Recommendation:
Reduce maxCookieAge to something shorter (e.g., 2 hours).
Implement a Refresh Token pattern or a server-side session blacklist.
### 3. Basic Password Complexity
Finding: isStrongPassword only requires 8 characters and 1 digit.
Risk: Weak passwords may be susceptible to brute-force or dictionary attacks.
Location: api/userHandlers.go:16
Recommendation: Enforce at least one uppercase, lowercase, and special character.
## 🚀 Performance & Stability Audit
### 4. IP Rate Limiter Memory Leak
Finding: IPRateLimiter.ips is a map that grows every time a new IP makes a request. There is no cleanup mechanism to remove old limiters.
Risk: In a production environment with many unique visitors, the backend will eventually run out of memory.
Location: api/middleware.go:47
Recommendation: Use a concurrent map with TTL or a simple periodic cleanup goroutine that removes entries older than X hours.
### 5. Missing Database Connection Limits
Finding: The database connection (sql.DB) is initialized without explicit limits on open or idle connections.
Risk: Under high load, the application could exceed the database's max_connections or waste resources keeping too many idle connections open.
Location: db/db.go:42
Recommendation: Set DB.SetMaxOpenConns(25), DB.SetMaxIdleConns(5), and DB.SetConnMaxLifetime(time.Hour).
### 🧠 Logic & Code Quality
### 6. Naming Inconsistency
Finding: The cookie is named session_id but contains a JWT.
Impact: Minor developer confusion.
Location: auth/middleware.go:70
Recommendation: Rename cookie to jwt_token or similar to clarify it's stateless.
### 7. Fixed Animation Wait Time
Finding: WaitForAnimationComplete uses a hardcoded 3-second timeout.
Impact: If the frontend animation takes longer than 3 seconds, the state broadcast might happen while the animation is still playing, causing a "jump" in the UI.
Location: api/serverMonitors.go:77
Recommendation: Make this configurable or use a more robust signaling mechanism if possible.
